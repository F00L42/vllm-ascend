本地 Codex 执行手册与每轮交付模板

日期：2026-09-18。此文件是普通项目开发说明，不是自动生效的 AGENTS.md 或已安装 skill。

1. 可直接交给本地 Codex 的任务

在当前 vllm-ascend main 基线的个人开发分支中，迁移 xllm-ops 的 MegaGdnMtpDecode 至 Ascend 910B。vllm、xllm、xllm-ops 为本地 submodule。先读本包 00 与 01，再按阶段读取 02–04。

核心原则：复用 Mega 的设备内融合计算结构，适配 vLLM 的状态契约。保留 vLLM 状态池、物理 checkpoint 映射、接纳后处理、prefix 所有权和请求生命周期。原版 slot×S ABI 不能直接用于 vLLM cache；non-FLA 仅解决 SSM 矩阵方向。核对 FP32 g 等数值差异，以当前 vLLM-Ascend 原生链为迁移基准。

你只有本地源码，不能连接服务器或运行 NPU 测试。每轮完成能本地验证的代码与测试，交付服务器可执行的构建/安装/测试说明、默认关闭的定向 telemetry 和回传规范。服务器随后拉取个人分支及精确 submodule 提交验证。不得把静态分析或 mock PASS 写成设备验证。

第一轮先做 P0：读取各级已有 AGENTS.md；记录父仓、三个 submodule 和实际 PTO 依赖的完整 SHA/dirty 状态；从当前源码画出调用与状态数据链；给出首版支持范围、数值差异表、计划修改文件和 CPU 契约测试。补足服务器基线采集所需代码，默认不改变原路径。已有基线证据充分时，可继续准备 P1 最小构建补丁，但其服务器执行状态保持 pending。

首版选择纯 spec、固定 S、eager、已验证 dtype/布局的路径；任何不支持配置在写状态前回退。融合边界必须包括 norm，确保 norm 恰好一次。launch 后异常不得在同一污染 cache 上直接跑原链。

每轮围绕一个明确假设工作；源码落到父仓可交付内容，避免未发布子仓修改。输出变更、实际本地检查、远端命令、预期证据、风险和下一步。不要根据旧文档硬写当前 API，也不要为尚未需要的模式大改 scheduler/cache manager。

2. 第一次会话先产出什么

顺序产物完成标准
1当前版本清单四仓 SHA + nested PTO + dirty 状态，实际路径来自 .gitmodules

本地没有运行 CPU 测试依赖时可用标准库验证索引模型；无法编译 CANN 不是停止所有准备工作的理由，但要保留明确边界。

3. 每日 rebase 的正确粒度

每日从当前 main 更新开发是用户约束；一轮远端验证必须冻结一次快照。不能让服务器拉父仓时又将子仓各自切到最新 main。

3.1 更新前

保存当前工作与上一轮证据关联，检查未提交改动。按当轮环境已有方式获得 main 更新；本手册不要求本地 Codex 额外访问 GitHub。以下为只读记录命令：

# 在 vllm-ascend 根目录
git rev-parse HEAD
git status --short
git submodule status --recursive
git show HEAD:.gitmodules

再对 .gitmodules 中真实子仓路径逐一记录 HEAD/status。父仓干净不能代替子仓干净；submodule status 的 +/- 等异常要解释。

3.2 更新后

由既有工作流完成个人分支 rebase；解决冲突后对下面敏感区域作语义差异检查，而不仅是确认没有 conflict marker：

  • gdn.py 的投影、core/norm 和 connector 钩子。

  • metadata builder 的 spec 分类、query 长度、padding/reset、accepted 来源。

  • runner 的 async、postprocess/precopy、request-slot 映射和 cache group。

  • cache shape/dtype/stride 与分配/共享策略。

  • 构建脚本、PTO/CANN 版本、torch schema/Fake 与图后端。

更新 source manifest，记录旧→新 SHA 与关键文件差异。旧测试结果归属旧 SHA，不改名当新结果。只运行与变更相关的必要本地检查；涉及 kernel、ABI、state 或图逻辑时安排对应服务器回归。

3.3 服务器复现

服务器 fetch 个人分支后检出指定 commit，并使用父仓 gitlink 对应的 submodule 提交；嵌套依赖同样固定。不要执行会各自追远端 main 的 submodule update --remote 作为实验同步步骤。

若 rebase 改写历史，仍保留 round_id → 完整 SHA → 服务端产物 → 结果的关联。可用已有团队保留机制保存实验 commit；不让报告只引用易变的分支名。

4. 功能模式与资格判定建议

以下为拟新增逻辑，不是现有环境变量：

  • off：完全原生路径，作为对照和回退基线。

  • auto：仅已验证的 shape/配置/metadata 命中候选，否则写状态前回退并在诊断模式记录原因。

  • force_for_test：只用于测试；不符合资格、包缺失或未命中候选即清晰失败，防止全 fallback 假 PASS。

候选功能开关与 telemetry 模式分开。首版默认 off；后续开启策略由服务器证据决定。

资格判定至少覆盖设备/包版本、dtype、heads/维度、Conv 参数、norm 参数、TP 后布局、S/B、纯 spec/等长、state stride/容量、有效索引协议、当前执行模式。大量动态设备值不要读回 host；优先用已有 CPU 元数据与生产端不变量。详细冲突检查放在测试/诊断路径。

5. 本地代码审查顺序

  1. 数学：是否遵循 vLLM 数值路径；scale、gate、norm 是否遗漏/重复？

  2. 地址：checkpoint 和 Conv 历史是否独立；是否使用真实 stride/64 位 offset？

  3. 所有权：共享读/独占写、跨请求别名、原位先读后写、异步依赖？

  4. 分发：运行时是否真命中；fallback 是否一定发生在写前？

  5. 构建：四仓/嵌套依赖是否能从服务器同样获得；包是否可能加载旧符号？

  6. 测试：reference 独立、跨轮、sentinel、非法输入、下一轮消费是否覆盖？

  7. 热路径：新增 .item()/.cpu()/synchronize、整池复制、每层重复转换是否有必要？

避免三类伪修复：将负 ID clamp 到 0；扩大浮点容差掩盖状态错误；异常后吞错并运行原链。

7. 服务器结果返回后的 Codex 提示词

先核对结果中的源码 SHA、环境、加载路径与本轮 manifest；确认候选是否实际命中，测试是否真正执行，是否存在 skipped。按“构建→加载→分发→地址/状态→数值→图/异步→性能”的顺序找到最早失败层。用 dump 重放或 CPU 契约模型定位第一处分歧，不根据最终文本猜测。只修改与证据直接相关的实现；若证据不足，补最小 telemetry 与实验，而不是同时大改多层。交付新的具体补丁和下一轮服务器指令，并更新已验证范围。

8. 日常项目状态文件建议

由本地 Codex 在父仓项目文档目录维护普通 Markdown/JSON：

  • source_manifest.json：当前开发基线及路径，不含机器凭据。

  • contract.md：已确认的当轮状态/数值契约，指向源码符号。

  • rounds/：每轮报告及结果摘要，较大 dump 按用户现有回传方式保管。

  • support_matrix.md：每种模式的 supported/fallback/pending 与证据 run_id。

不要将本资料包全文重复塞进每个文件。主开发计划描述目标，契约文件描述接口，round 报告描述证据。下一次会话先读最新状态和失败材料，再决定工作。

9. 明确不做的范围

本项目初期不迁移整个 xLLM 运行时，不替换 vLLM scheduler/cache manager，不扩展到 310P/950，不顺带迁移 prefill/draft/single-token Mega，不以重写拒绝采样为本轮目标。后续扩展必须有实际需求与性能证据。

Skills 可以提供 Ascend C/PTO、精度、profiling 方法，但不能强制本地 Agent 执行 SSH/NPU 流程，也不能改变本包的服务器分工。无需为了阅读本包额外安装技能。已有仓库指令与当前用户约束结合执行。
